## 背景

- TransPaper（ローカルPDF翻訳）を論文ページに組み込んで、チームにも翻訳PDFを見せられないか検討した
- 結論は見送り。GitHub Pages ではサーバーを動かせないうえ、arXiv 論文の約4割は翻訳版を再配布できないライセンスだった（最新30本の内訳: CC BY 17本 / arXiv non-exclusive 11本 / NC系 2本）。PyMuPDF も AGPL
- TransPaper は今まで通り自分だけで使い、面白い論文は Slack に手動で共有する運用にした
- そのかわり、論文とニュースの「閲覧コスト」を下げる改修を行った

## 論文ページ（collect_hf_papers.py）

| 機能 | 内容 |
|---|---|
| NEW バッジ | 前日以前の最新記事に載っていなかった論文に付ける。7日分のウィンドウで集めているため、毎回約2/3が前日と重複していた |
| タブ件数 | `ALL(30) NEW(11) Agent(18) ...` |
| ELI5要約 | 「どんな問題？／どうやった？／何がうれしい？」の3項目×100〜150字。「要約を読む」の折りたたみで表示 |

### ELI5要約の仕組み

- 送るのは要約がまだない論文だけ。要約は記事HTMLの `data-eli5` 属性に入れておき、次回はそこから再利用する
- プロンプトを変えたら `ELI5_VERSION` を上げる。古い版の要約は作り直される
- Gemini は flash-lite（thinkingLevel=low）を使う。モデル名はモデル一覧APIから最新の安定版を自動で選ぶ（現時点では `gemini-3.5-flash-lite`）。503・タイムアウト・1日の枠切れのときは、予備の `gemini-3.8-flash` に切り替える。環境変数 `GEMINI_MODEL` でモデルを固定することもできる
- 失敗したモデルは後回しにし、Gemini に使う時間は合計5分まで。それでも要約できなかった論文は英語の abstract で表示し、次回の実行で要約する
- `responseSchema` で JSON の形を固定している。abstract に書かれていないことは書かないように指示している

### 試したがやめたもの

| 方式 | やめた理由 |
|---|---|
| Google翻訳（deep-translator） | ローカルPCも GitHub Actions のIPもブロックされた |
| abstract の全文翻訳 | 翻訳しても研究者向けの文章で頭に入らなかった |
| 1行要約（ai_summary） | 短すぎた |
| 30本を1回で送る | 返事が遅くなってタイムアウトしやすく、失敗したときに全部が英語に戻る。5本ずつに分けた |

## ニュースページ（collect_daily_news.py）

### 画面

```
[Zenn] [Qiita] [はてな] [Blog] [HN] [Slides] [ALL]
[Latest] [Hotness] [NEW n]                         ← 全タブ共通。NEW は新着だけに絞る
[セキュリティ n] [AIエージェント n] ...              ← ALL タブのときだけ表示
```

- ALL タブには全ソースの記事をまとめ、NEW を先頭に並べる。NEW の最後に区切り線を表示する。各記事に出典ラベルを付けた
- 分野の絞り込みでは、分野同士は OR、NEW とは AND
- 記事ごとの NEW バッジは見づらかったので削除し、絞り込みと ALL タブの並び順だけで新着が分かるようにした
- GitHub タブは削除した。データ元（yashikota/github-trending-ja）が a-kaibu/github-trending に移転したうえ、10-06 から更新が止まっているため。復活したら git の履歴から戻せる

### 分野分類（1記事1分野、MECE）

セキュリティ / AIエージェント / LLM・生成AI / ML・データ / インフラ・運用 / Web・アプリ / 言語・開発ツール / キャリア・組織 / 業界・製品 / その他

- タイトルのキーワード一致数がいちばん多い分野にする（1件3点）。同点なら上の並び順で決める
- 説明文は、タイトルでどの分野にも当たらなかったときだけ使う（説明文が判定を覆す誤分類が多かったため）
- 「AI」「人工知能」は弱いキーワード（1点）。ほかの分野に当てはまらなければ LLM・生成AI にする
- 英数字のキーワードは単語単位で照合する（evaluation が lua、organization が gan に反応する誤りがあった）
- 長いキーワードから順に照合し、一致した部分を消す（"claude code" が当たったら "claude" は数えない）
- 「その他」は 33% から約 7〜14% に減った。残りは主に HN の技術以外の話題

## 運用メモ

- Gemini の無料枠は太平洋時間0時（JST 16時、冬時間は17時）にリセットされる。枠はモデルごとに別
- 毎日の運用では NEW の論文が約10本なので、Gemini には2〜3回送るだけで済む。ワークフローは全体で2〜3分の見込み
- `.pyc` を git の管理から外し、`.gitignore` に `__pycache__/` を追加した
- Slack 通知は JST 12:00:00 ちょうどに送る。cron-job.org で 11:55 に起動し、準備ができたら 12:00 まで待ってから送る（10分前より早く準備できた場合と、12:00 を過ぎた場合は待たずに送る）。起動から準備完了まではおよそ2分で、そのうち GitHub Pages のビルド待ちが50〜80秒を占める
- 手動実行のときは `notify_at`（JST の HH:MM）で送信時刻を指定できる
- 手動実行でも Slack に送られる。実行前に `SLACK_CHANNEL_ID` が本番の値かどうかを確認すること

## 残っている課題

- 分類は完全ではない。インフラとセキュリティが同点になる記事などは判断が分かれる。誤分類を見つけたら、キーワードを `GENRES` に追加して直す
- flash は混雑していることが多く、試し実行では flash-lite のほうが速く安定していた。そのため最初から flash-lite を使う構成にした
